    15. Spring IoC

    15.1. مقدمة

    نقترح اكتشاف إمكانيات تكوين وتكامل إطار عمل Spring (http://www.springframework.org) وكذلك تعريف واستخدام مفهوم IoC (انعكاس التحكم)، المعروف أيضًا باسم حقن التبعية (Dependency Injection)

    لننظر إلى التطبيق ثلاثي الطبقات الذي قمنا بإنشائه للتو:

    للاستجابة لطلبات المستخدم، يجب أن يتواصل وحدة التحكم [Application] مع الطبقة [service]. في مثالنا، كانت هذه الطبقة مثيلًا من النوع [DaoImpl]. حصلت وحدة التحكم [Application] على مرجع على الطبقة [service] في طريقتها [init] (الفقرة 14.8.3):

    • السطر 6: تم إنشاء مثيل للطبقة [dao] عن طريق إنشاء مثيل صريح لـ [DaoImpl]
    • السطر 9: تم إنشاء مثيل للطبقة [service] عن طريق إنشاء مثيل صريح لـ [ServiceImpl]

    تجدر الإشارة إلى أن الفئتين [DaoImpl] و [ServiceImpl] تنفذان واجهات، وهما واجهتا [IDao] و [IService] على التوالي. في الإصدارات القادمة، سيتم تنفيذ واجهة [IDao] بواسطة فئة تدير قائمة بالأشخاص المخزنة في قاعدة البيانات. لنسمي هذه الفئة [DaoBD] في هذا المثال. سيتطلب استبدال تنفيذ [DaoImpl] للطبقة [dao) بتنفيذ [DaoBD] إعادة تجميع الطبقة [web]. في الواقع، يجب الآن أن تقوم السطر 6 أعلاه، الذي يقوم بإنشاء مثيل للطبقة [dao] بنوع [DaoImpl]، بإنشاء مثيل لها بنوع [DaoBD]. وبالتالي، فإن طبقتنا [web] تعتمد على الطبقة [dao]. ويُظهر السطر 9 أعلاه أنها تعتمد أيضًا على الطبقة [service].

    سيسمح لنا Spring IoC بإنشاء تطبيق ثلاثي الطبقات حيث تكون الطبقات مستقلة عن بعضها البعض، c.a.d. بحيث لا يتطلب تغيير إحداها تغيير الطبقات الأخرى. وهذا يوفر مرونة كبيرة في تطوير التطبيق.

    ستتطور البنية السابقة على النحو التالي:

    مع [Spring IoC]، سيحصل وحدة التحكم [Application] على المرجع الذي تحتاجه في الطبقة [service] بالطريقة التالية:

    1. في طريقة [init] الخاصة به، سيطلب من الطبقة [Spring IoC] تزويده بمرجع على الطبقة [service]
    2. ثم سيستخدم [Spring IoC] ملف التكوين XML الذي يحدد له الفئة التي يجب إنشاء مثيل لها وكيفية تهيئتها.
    3. تقوم [Spring IoC] بإرجاع مرجع الطبقة [service] التي تم إنشاؤها إلى وحدة التحكم [Application].

    ميزة هذا الحل هي أن أسماء الفئات التي تُنشئ مثيلات الطبقات المختلفة لم تعد مكتوبة بشكل ثابت في طريقة [init] في وحدة التحكم، بل أصبحت موجودة ببساطة في ملف التكوين. سيؤدي تغيير تنفيذ إحدى الطبقات إلى تغيير في ملف التكوين هذا، ولكن ليس في وحدة التحكم.

    لنستعرض الآن إمكانيات [Spring IoC] باستخدام أمثلة.

    package istia.st.springioc01;

public class Personne {

    // الخصائص
    private String nom;
    private int age;

    // عرض الشخص
    public String toString() {
        return "nom=[" + this.nom + "], age=[" + this.age + "]";
    }

    // init-close
    public void init() {
        System.out.println("init personne [" + this.toString() + "]");
    }

    public void close() {
        System.out.println("destroy personne [" + this.toString() + "]");
    }

    // مُستردات-مُعيّنات
    public int getAge() {
        return age;
    }

    public void setAge(int age) {
        this.age = age;
    }

    public String getNom() {
        return nom;
    }

    public void setNom(String nom) {
        this.nom = nom;
    }

}

    • السطور 6-7: حقلان خاصان هما الاسم والعمر
    • السطور 23-38: طرق القراءة (get) والكتابة (set) لهذين الحقلين
    • السطور 10-12: طريقة toString لاسترداد قيمة الكائن [Personne] في شكل سلسلة أحرف
    • السطور 15-21: طريقة init التي سيتم استدعاؤها بواسطة Spring عند إنشاء الكائن، وطريقة close التي سيتم استدعاؤها عند تدمير الكائن

    <bean id="personne2" class="istia.st.springioc01.Personne" init-method="init" destroy-method="close">

    • السطران 3 و 12: العلامة <beans> هي العلامة الجذرية لملفات تكوين Spring. داخل هذه العلامة، تُستخدم العلامة <bean> لتعريف الكائنات المختلفة المراد إنشاؤها.
    • الأسطر 4-7: تعريف bean
    • السطر 4: يُسمى bean [personne1] (السمة id) وهو مثيل للفئة [istia.st.springioc01.Personne] (السمة class). سيتم استدعاء الطريقة [init] للمثيل بمجرد إنشائه (السمة init-method) وسيتم استدعاء الطريقة [close] للمثيل قبل تدميره (السمة destroy-method).
    • السطر 5: يحددان القيمة التي ستُعطى للخاصية [nom] (السمة name) للمثيل [Personne] الذي تم إنشاؤه. لإجراء هذا التهيئة، سيستخدم Spring الطريقة [setNom]. لذلك يجب أن تكون هذه الطريقة موجودة. وهذا هو الحال هنا.

    package istia.st.springioc01;

import org.springframework.beans.factory.xml.XmlBeanFactory;
import org.springframework.core.io.ClassPathResource;

public class Main {

    public static void main(String[] args) {
        // استخدام ملف تكوين Spring
        final XmlBeanFactory bf = new XmlBeanFactory(new ClassPathResource("spring-config-01.xml"));
        // استرداد bean [personne1]
        Personne personne1 = (Personne) bf.getBean("personne1");
        System.out.println("personne1=" + personne1.toString());
        // استرداد bean [personne2]
        Personne personne2 = (Personne) bf.getBean("personne2");
        System.out.println("personne2=" + personne2.toString());
        // استرداد bean [personne2] مرة أخرى
        personne2 = (Personne) bf.getBean("personne2");
        System.out.println("personne2=" + personne2.toString());
        // حذف جميع الفاصوليا
        bf.destroySingletons();
    }
}

    • تم الحصول على السطر 1 من خلال تنفيذ السطر 12 من [Main]. العملية 
    Personne personne1 = (Personne) bf.getBean("personne1");

    أجبرت على إنشاء bean [personne1]. نظرًا لأننا كتبنا [init-method="init"] في تعريف bean [personne1]، فقد تم تنفيذ الطريقة [init] للكائن [Personne] الذي تم إنشاؤه. يتم عرض الرسالة المقابلة.

    • السطر 2: أدى السطر 13 من [Main] إلى عرض قيمة الكائن [Personne] الذي تم إنشاؤه.
    • السطران 3-4: تكرر نفس الظاهرة بالنسبة للفول المسمى [personne2].
    • السطر 5: عملية السطرين 18-19 من [Main] 
        personne2 = (Personne) bf.getBean("personne2");
    System.out.println("personne2=" + personne2.toString());

    لم تؤدِ إلى إنشاء كائن جديد من النوع [Personne]. لو كان الأمر كذلك، لكانت طريقة [init] قد ظهرت. هذا هو مبدأ singleton. لا ينشئ Spring، بشكل افتراضي، سوى نسخة واحدة من البينات الموجودة في ملف التكوين الخاص به. إنها خدمة مراجع الكائنات. إذا طُلب منها مرجع كائن لم يتم إنشاؤه بعد، فإنها تنشئه وتقدم مرجعًا له. إذا كان الكائن قد تم إنشاؤه بالفعل، فإن Spring تكتفي بتقديم مرجع له. هنا، نظرًا لأن [personne2] قد تم إنشاؤه بالفعل، فإن Spring تكتفي بتقديم مرجع له.

    • تم عرض السطور 6-7 بواسطة السطر 21 من [Main] الذي يطلب تدمير جميع الفاصوليا المشار إليها بواسطة الكائن [XmlBeanFactory bf]، وبالتالي الفاصوليا [personne1, personne2]. ونظرًا لأن هذين الكائنين (beans) لهما السمة [destroy-method="close"]، يتم تنفيذ الطريقة [close] الخاصة بهما، مما يؤدي إلى عرض السطرين 6 و7.

    بعد أن أصبحنا الآن على دراية بأساسيات تكوين Spring، سنكون أسرع قليلاً في شرحنا.

    15.3. تكوين تطبيق متعدد الطبقات باستخدام Spring

    لنفترض أن لدينا تطبيقًا ثلاثي الطبقات له الهيكل التالي:

    utilisateurDonnéesCouche المهنة [metier] طبقة الوصول إلى البيانات [dao] طبقة واجهة المستخدم [ui]

    نقترح هنا إظهار أهمية Spring في بناء مثل هذه البنية.

    • ستصبح الطبقات الثلاث مستقلة بفضل استخدام واجهات Java
    • سيتم تحقيق تكامل الطبقات الثلاث بواسطة Spring

    قد تكون بنية التطبيق في Eclipse كما يلي:

    • [1]: الطبقة [dao]:
      • [IDao]: واجهة الطبقة
      • [Dao1, Dao2]: تطبيقان لهذه الواجهة
    • [2]: الطبقة [metier]:
      • [IMetier]: واجهة الطبقة
      • [Metier1, Metier2]: تطبيقان لهذه الواجهة
    • [3]: الطبقة [ui]:
      • [IUi]: واجهة الطبقة
      • [Ui1, Ui2]: تطبيقان لهذه الواجهة
    • [4]: ملفات تكوين Spring للتطبيق. سنقوم بتكوين التطبيق بطريقتين.
    • [5]: المكتبات اللازمة للتطبيق. وهي المكتبات المستخدمة في الأمثلة السابقة.
    • [6]: حزمة الاختبارات. سيستخدم [Main1] التكوين [spring-config-01.xml] وسيستخدم [Main2] التكوين [spring-config-02.xml].

    15.4. الخلاصة

    يتمتع التطبيق الذي قمنا بإنشائه بمرونة كبيرة في التطور. يمكن تغيير تنفيذ طبقة ما بمجرد التكوين. ويبقى كود الطبقات الأخرى دون تغيير. ويتحقق ذلك بفضل مفهوم IoC الذي يعد أحد ركيزتي Spring. الركيزة الأخرى هي AOP (البرمجة الموجهة نحو الجوانب) التي لم نعرضها. وهي تسمح بإضافة "سلوك" إلى طريقة فئة، أيضًا عن طريق التكوين، دون تعديل كودها.
